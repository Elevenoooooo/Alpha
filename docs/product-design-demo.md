# 产品设计对话 Demo

本次目标：用户先看懂 Alpha 要怎么做，再快速找到会影响产品选择的结论；详细依据和参数在需要时展开。没有接入模型、经营数据、真实定价或询报价接口。

## 三个场景

| 案例 | 正文形态 | 产品结果 |
| --- | --- | --- |
| 黑胶唱片机 · 明确推荐 | 主结论 + 两段解释，重点说明耗材需求与线上整机品的关系 | 三张卡，仅耗材权益标优先推荐；替代品与互补品分别标识 |
| 翻译机 · 方案比较 | 主结论 + 三行对照表 + 一段关键价差解释 | 三张卡，不强制选第一名；不同责任需要按诉求取舍 |
| 单反相机 · 依据不足 | 主结论说明不能定价 + 可保留方向 + 补数提示 | 不输出价格、推荐机型及可采纳产品卡，交付设计记录 |

入口：左侧「产品设计演示」；会话顶部切换案例。点击当前案例可重新演示。约 10 秒完成一次演示，耗时按本地实际运行计时。执行中无需确认。

## 模型、前端与 UI 的责任

| 内容 | 模型侧 | 前端侧 | UI 侧 |
| --- | --- | --- | --- |
| 计划的一句话 | 解释本任务如何开展；不重复用户目标，不写抽象方法名 | 独立字段 `plan.lead`，随计划内容一起展开或收起 | 展开时作为计划的视觉重点，收起时隐藏 |
| 计划步骤 | 通常三步，2–4 步均可；标题包含本任务的行动和对象，如“查耗材保障空位”，避免套“形成产品建议”等通用标题 | 按数组渲染，执行中展开、完成后收起，允许再次展开 | 标题和说明均为 14px，标题加粗、说明用较深灰色；宽屏对齐排列，窄屏上下排列 |
| 执行范围及必要假设 | 只保留会改变结果的类目、渠道、责任边界；明确容易混淆的对象或期限，不填默认套话 | `scope` 紧跟重点句，随步骤折叠；重要 `note` 保持可见 | 13px 范围信息放在浅色底条中，让用户先核对边界，再看行动步骤 |
| 主结论 | Markdown 第一行用 `##` 写实际建议；影响成立的缺口在此说清楚 | Markdown 渲染，不依赖“总体建议”等词识别 | 首个二级标题略大、适度加粗 |
| 正文 | 在自然段、短列表、表格中择需组织；只保留影响选择的差异与证据 | 保持 Markdown 自由结构，支持 GFM 表格和引用按钮 | 统一段落间距、表格与强调样式；不强制章节 |
| 用户需处理事项 | 只有真实事项才输出，不自动生成“待确认” | `actionRequired` 可为空；为空时不占位 | 有值才显示浅色提示块 |
| 产品标签 | 判断优先程度与线上关系，明确对标对象和理由 | 推荐布尔值 + 替代/互补枚举；推荐产品置于货架首位，其余保持原顺序；无推荐时保持原顺序 | 推荐用紫底，替代与互补用低饱和标签；同卡可有两种维度 |
| 过程与证据 | 正式接入时提供可对外展示的步骤结果、来源、缺口 | 状态、耗时来自任务事件；按引用 ID 打开对应依据 | 默认收起，点击“思考完成”或引用打开右侧摘要 |

### 正文精简约定

先写最重要的判断，再选择解释。判断一句话不够时，只补会改变用户选择的差异，如责任边界、对标线上品关系、价格差异、履约条件或人群适配。每个关键判断保留最有用的依据；不要逐款复述卡片参数，不固定输出市场、人群、定价等完整章节。约 150–300 字是编辑目标，不是截断条件；必要的不确定性不能为了字数被省略。完整责任、字段、证据放入决策文档。

当前前端承接的最小结构为 `plan + answerMarkdown + actionRequired? + products + evidence + process + document`。这是演示数据契约，尚未修改实际模型 Prompt 或后端协议。现有算法若仅输出一个 Markdown 字符串，可先约定主结论使用首个 H2；结构化卡片和可选事项应由明确的分段或消息类型提供，不建议前端靠关键字猜语义。

## 可以操作的交互

- 计划展开/折叠；输入框调整；完成后正文展示。
- 过程侧栏、正文引用、文档内引用跳转。
- 文档全文、Markdown 下载、带入当前文档到 Wiki。
- 产品详情、使用方案、我的产品中的详情和询价流程。
- 产品、正文、文档共享案例数据；价格和服务字段不另写副本。

输入框调整是有限的 Demo 指令，并非模型理解。可试：「只做 C 延保」「只做电销」「先看人群」「暂不定价」；也可用逗号组合，例如「只做 C 延保，暂不考虑电销」。同类后续要求以最后一次为准，保留前一轮对话；执行中提出新要求会停止上一轮。无法识别的要求及文件分析不会被假装应用，输入保留并提示范围。单反案例补数不会触发真实分析。

“通过”为演示评审状态；标签、价格、对标对象和服务资源均为案例设定。过程面板展示公开的执行摘要，不代表真实模型内部推理。

## 检查方式

运行 `pnpm check`、`pnpm build`、`node scripts/verify-design-cases.mjs`。

浏览器应覆盖：三个案例自动完成与计划折叠、推荐仅出现于推荐场景、比较表、缺失数据场景无产品货架、引用和详情匹配、文档下载与 Wiki 附件、采纳后进入待询价、执行中调整与快速切换不混入旧结果、桌面和窄屏不溢出。

这些检查验证本地演示的内容一致性与交互；没有进行真实模型评测、线上业务验收或用户阅读效率实验。

### 本次实际验证（2026-09-18）

- 类型检查、构建、案例一致性检查通过。构建存在单个包超过 500 KB 的体积提示，不影响本地预览；未测量真实性能收益。
- 桌面浏览器逐一检查三个场景：自动执行、完成后计划收起；推荐数量分别为 1、0、0；比较场景展示三行表格；单反场景产品卡数量为 0。
- 黑胶正文引用打开对应依据；文档内引用跳转到相应段落；Markdown 已下载到本机，Wiki 带入附件名称与当前案例一致。
- 推荐产品详情字段与卡片一致；采纳后按钮禁用，并在「我的产品」呈现为待询价。
- 执行中输入「只做 C 延保，暂不考虑电销」后，旧轮停止，仅新轮生成结果；渠道及产品标识更新。输入「价格改成 1 元」会被明确拒绝应用。
- 390 px 窄屏检查中，正文与输入框没有页面级横向溢出；1280 px 桌面产品货架保持三列。

### 计划清单的后续优化
